# 복붙용 프롬프트

아래 전문을 LLM에 붙여넣고, 맨 아래 `<모델>` 자리에 검토할 모델 폴더 이름을 적는다
(예: `deepseek-ai__DeepSeek-V4-Pro`). 저장소 파일을 읽을 수 있는 환경이어야 한다.

---

당신은 llm-arch-tracer 가 뽑은 **operator별 tensor shape 라벨**을 검토한다.

이 도구는 HuggingFace 모델을 meta device에서 트레이스해 연산마다 입력·가중치·출력 shape을
기록하고, 각 축에 `d_model`, `n_h`, `d_head` 같은 이름을 붙인다. 이름은 등록된 규칙이 붙이고,
규칙이 자기 일관성을 검사하는 게이트도 이미 통과했다. **당신이 볼 것은 규칙이 구조적으로 볼 수
없는 것이다** — 규칙 자체가 틀렸거나, 두 config 값이 이 seq_len에서 우연히 같아 값으로는
어느 이름인지 가릴 수 없는 축.

## 먼저 읽을 것

1. `review/01-procedure.md` — 판정 절차와 판정 4종
2. `review/02-evidence.md` — 증거가 어디 있는지
3. `review/03-output.md` — 결과를 어떤 형식으로 남기는지
4. `review/04-full-inventory.md` — **전수조사 방법론**: 무엇이 모집단이고, 어느 층까지 기계가
   결론을 냈고, 당신이 볼 것은 그중 무엇이며, 안 본 것을 어떻게 기록하는지
5. `review/05-overrides.md` — 판정을 **산출물에 반영**하는 법(근거 인용 필수)
6. `models/<모델>/review_request.md` — **이 모델에서 판단이 필요한 것 + 전수 점검 목록**

## 어디서 시작하나 — 의뢰서 **0절**

파이프라인이 **"규칙으로는 여기까지"라고 스스로 선언한 축**이 거기 실려 있다. 값으로는 결정할
수 없어 넘긴 자리이고, 사유는 셋뿐이다:

| 사유 | 뜻 |
|---|---|
| `tie` | 두 개 이상의 심볼이 같은 값이라 전역 우선순위(=관례)로 이겼다 |
| `heur` | 등록된 규칙이 없어 산술로 지어낸 이름이다 |
| `bare` | 이름을 못 붙였는데 크기가 커서(≥64) 진짜 차원일 수 있다 |

**값이 같은 심볼이 여럿이면 값으로는 영원히 못 가른다. shape 안의 위치가 말해 준다** —
`[B, n_h, T, d_head]` 에서 축 1 은 head 개수, 축 3 은 head 폭이다. 그래서 0절 표에는 축 위치와
표본 shape 이 같이 실려 있다. 실제로 Kimi 계열은 `d_head == d_rope == n_h == n_kv == 64` 라
위치 말고는 가릴 방법이 없다.

**답하는 법**: 소스에서 그 폭을 만드는 줄을 찾고, 0절 아래의 초안에서 `to` 와 `source` 두 줄만
채워 `rules/label_overrides.yaml` 에 넣는다. **나머지 줄은 하나도 지우지 말 것** —
`shape`/`axis`/`field`/`shape_index`/`op_type`/`nth` 여섯이 함께 **그 축을 처음 만든
자리(앵커)를 유일하게 지목**한다. 그중 하나라도 빠지면 엉뚱한 축까지 잡는다: Kimi 의
`[B, n_h, T, d_nope]` 축 3 은 `shape`+`axis` 만으로는 **366개 등가류**를 동시에 잡고
(q 의 q_pass, KV 의 k_nope, value_states …), 하나를 고치면 나머지가 망가진다.

유일성은 파이프라인이 **실제로 돌려 봐서** 검증한다 — 그 조건에 맞는 자리가 몇 개의 등가류에
속하는지 세고, 한 레이어 안에서 둘 이상이면 `stub_ambiguous` 를 붙인다. 붙어 있으면 그 초안은
쓰지 말고 `open` 으로 남긴다. `spread: class` 가 붙어 있어
**그 축이 지나는 모든 자리가 한 번에** 바뀐다 — 모듈 경계에서 멈추지 않는다. 예전에는 그것이
멈춰서 소스로 확정한 교정 58건이 반영되지 못했다.

크기-1 축과 루프 카운터는 0절에 없다 — **이름이 없는 게 정답**이라 애초에 넘기지 않는다.

**이미 답한 질문은 다시 올라오지 않는다.** 교정이 실제로 손댄 축은 인계 목록에서 종결
처리된다(`src/label_overrides.apply` 가 손댄 슬롯을 기록하고 `axis_classes.unsettled` 가 그
등가류를 뺀다). 그러니 0절에 남아 있다면 아직 답하지 않은 것이다 — 정답을 다시 넣어
`applied: 0` 인 죽은 교정을 만들 일이 없다. 2026-08-14 까지는 이 회계가 닫혀 있지 않아
교정한 축이 재생성마다 되살아났다(외부 검토가 짚었다).

## 자세 — 확인하지 말고 **반박하라**

이 절이 나머지 전부보다 중요하다.

**"이 라벨이 맞습니까?"라고 물으면 LLM은 대체로 "네, 맞습니다"에 그럴듯한 근거를 붙여 답한다.**
같은 모델, 같은 자료를 줘도 프레임을 바꾸면 잡아내는 양이 크게 달라진다 — 외부 검토가
우리보다 훨씬 많이 찾아낸 이유가 이것이었다(2026-08-12).

그러니 이렇게 물어라:

> **이 산출물에 회귀와 할루시네이션이 있다고 가정한다. 증거를 찾아라.**
> **최근 "고쳤다"고 적힌 항목들이 실제로는 실패했다는 증거를 먼저 찾아라.**

- 한 라벨을 볼 때 "왜 맞는가"가 아니라 **"어떤 모습이면 이게 틀린 것인가"를 먼저 정하고**,
  그 모습이 실제로 있는지 본다. 없으면 그때 맞다고 적는다.
- 최근 교정(`rules/label_overrides.yaml`, `review_findings.md` 의 `status: fixed`)은
  **한쪽만 고쳤을 가능성이 가장 높은 자리**다. 실제로 그런 사례가 두 번 나왔다 — 피연산자만
  고치고 가중치를 방치했고, `E` 만 바꾸고 같은 축의 정수 `32` 를 남겼다.
- 근거 문장이 실측과 맞는지도 의심하라. **결론이 맞아도 근거가 지어낸 것일 수 있다.**

## 반드시 지킬 것

- **소스를 연다.** `develop/sources/modeling_*.py` 에 이 모델의 실제 코드가 이미 받아져 있다.
  문제의 shape을 만드는 **코드 줄**을 찾아라. 구조를 일반론으로 설명하지 말고 그 줄을 인용해라.
- **HF 소스는 출발점이지 울타리가 아니다. 부족하면 필요한 소스를 직접 찾아라.**
  캐시된 파일에 답이 없는 경우는 흔하다 — 연산이 Triton·CUDA 커스텀 커널이라 HF 에는 torch
  fallback 만 있거나(KDA, mamba-ssm, causal-conv1d, flash-attn) 아키텍처가 아직 transformers
  본체에 없어 remote code 로 도는 경우다. **우리 트레이스는 그 fallback 을 돈 것이므로 실제
  커널과 다를 수 있다.** 그럴 땐 알아서 찾아본다: 모델 저장소의 remote code, vLLM / SGLang /
  TensorRT-LLM 독립 구현, 커널 저장소, 논문, 공식 블로그·model card, GitHub 이슈·PR — 무엇이든
  답을 주는 것이면 된다. 아래 순서는 보통 이 순서가 빠르다는 **권고**지 제한이 아니다:

  > 실행 중인 modeling 소스 → config 클래스 docstring → 모델 저장소 remote code →
  > vLLM/SGLang/TRT-LLM → 커널 저장소 → 논문 → model card·블로그 → 검색

  무엇을 봤는지는 근거에 URL 로 남긴다. 어디를 봐도 답이 없으면 **본 곳을 적고**
  `undetermined` 로 남긴다 — 짐작으로 메우지 않는다.
- **한 op 안의 모든 필드가 서로 일치하는가를 별도로 확인하라.** 필드를 각각 소스와 맞대는
  것만으로는 부족하다 — 같은 행의 `input_shape` / `weight_shape` / `output_shape` 를 **서로**
  대조해야 보이는 결함이 있다:
    - 가중치는 `[out_features, in_features]` 로 저장되고 matmul 은 그 **전치**를 먹는다.
      두 표기가 같은 텐서를 가리키는지, 축 순서 규약이 q/k/v/o 전부에서 같은지.
    - `[m,k] @ [k,n] -> [m,n]` 의 세 이름이 실제로 합성되는지.
    - 전치·view 처럼 **이름을 바꿀 수 없는 op** 이 이름을 바꾸지 않았는지.
- **의뢰서 항목 수와 판정 수를 직접 세어 맞춰라.** "다 봤다"는 서술을 믿지 말고 개수를 diff 하라.
  (게이트도 이제 이걸 검사하지만, 검토자가 스스로 확인하는 것이 원칙이다.)
- **우리 자체 산출물을 검증으로 믿지 말 것.** `model_summary.md` 의 체크리스트나
  `review_findings.md` 는 참고다. 실제로 `full/*.csv` 와 `*.jsonl` 을 세어 확인해라 —
  의뢰서가 낸 질문 수와 답한 수가 맞는지, `full/ambiguous.json` 의 `chosen` 이 채워졌는지까지.
  "검토했다"고 적혀 있지만 안 한 경우가 실제로 여러 건 있었다(2026-08-12 외부 검토).
- **접힌 표(`prefill.jsonl` / `decode.jsonl`)는 샘플링 없이 한 줄씩 훑어라.** 모델당 수백 줄이라
  전부 읽을 수 있다. 한 행 안에서 `input_shape` / `weight_shape` / `output_shape` 가 서로
  말이 되는지는 A/B/C 절의 접힌 뷰에서 보이지 않는다 — 그렇게 4,406건이 숨어 있었다.
- **소스가 transformers 본체에 없으면 모델 저장소를 열어라.** `develop/sources/` 에
  `<model_id>__<파일명>.py` 로 이미 받아뒀을 수 있다. 파일 이름은 model_type 과 다를 수 있고
  (Kimi-K2.6 → `modeling_deepseek.py`), 판정에는 실제로 읽은 파일을 인용한다.
- **근거 없는 판정은 판정이 아니다.** 클래스·메서드 이름과 인용한 코드 줄이 있어야 한다.
  **게이트가 이걸 검사한다**: `should_be_renamed` 판정의 근거에 파일명(`modeling_*.py` /
  `configuration_*.py`)이나 URL이 없으면 FAIL이다. "이 이름은 틀렸고 저 이름이 맞다"는
  소스에 대한 주장이므로 무엇을 읽었는지 말해야 한다. 이 규칙은 2026-08-12까지 문서에만
  있고 아무도 강제하지 않았고, 그래서 판정 187건 중 101건에 인용이 없었다.
- **모르면 `undetermined`. 단, 그것도 비용을 치른다.** 무엇을 봤고 뭐가 없었는지 적는다.
  **게이트가 검사한다**: `undetermined` 판정의 근거에 URL 이 하나도 없으면 FAIL 이다.
  캐시된 HF 소스는 출발점이지 울타리가 아니므로, 거기서 못 찾았다면 저장소 remote code /
  vLLM·SGLang / 커널 저장소 / 논문 / model card 중 **어디를 봤는지 URL 로** 남아 있어야 한다.
  URL 이 없다는 건 HF 소스만 보고 포기했다는 뜻이고, 그건 "확인 못함"이 아니라 "안 해봄"이다.
  2026-08-13 전수 재검토에서 `undetermined` 13건 중 **10건이 오분류**였다 — 근거 문장이
  질문을 바꿔치기하고 있었다("이 축이 무엇인가" → "**트레이스만으로** 가를 수 있나").
  소스는 답을 갖고 있었고, 막는 건 지식이 아니라 표현 수단이었다.
  **모르는 것과 못 넣는 것을 같은 칸에 적지 마라.**
- **정수를 억지로 이름 붙이지 않는다.** 루프 인덱스·피연산자 개수는 이름이 없는 게 정답이다.
