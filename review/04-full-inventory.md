# 04. 전수조사 — 방법론

`01-procedure.md` 는 **미결 안건**을 어떻게 판정하는지를 다룬다. 이 문서는 그보다 앞선 질문에
답한다: **미결 목록에 오르지도 않은 이름까지 전부 확인하려면 어떻게 해야 하는가.**

필요한 이유는 실제 사고에서 나왔다. DeepSeek-V4-Pro 의 mHC 혼합 행렬이 `[B, 1, 4, d_model]` 로
렌더됐고 그 `4` 는 `n_hc` 였다. 그 축은 네 가지 미결 범주 **어디에도** 오르지 않았다 — 휴리스틱도
아니고, 정사각도 아니고, 별칭 공백도 아니고, 미등록 필드도 아니었다. 그냥 아무도 볼 이유가
없었던 정수였고, 독자가 CSV 에서 찾아냈다(2026-08-10). **열린 질문 목록은 우리가 이미 물을 줄
아는 질문만 담는다.**

---

## 1. 무엇이 "전수"인가 — 모집단을 먼저 센다

세지 않은 것을 전수라고 부를 수는 없다. 의뢰서의 전수 점검 절은 기계가 세어서 만든다.

| 절 | 무엇 | 현재 함대 (36개 모델) |
|---|---|---|
| A | 붙은 이름 × 나타나는 모듈 | **779행** |
| B | 이름 없이 남은 (모듈, 정수) 쌍 | **302행** |
| C | (모듈, 출력 shape) 쌍 | **13,830행** |
| | **합계** | **14,911행** |

이 숫자는 `models/<모델>/review_request.md` 에서 그대로 세어진다. 늘거나 줄면 그것도 사실이다.

## 2. 왜 "14,911행을 다 읽었다"가 답이 아닌가

읽었다는 주장은 검증할 수 없다. 균일하게 읽었다는 주장은 더더욱 그렇다. 그리고 정확도를
목표로 하는 절차에서 **확인되지 않은 판정이 확인된 판정과 같은 표에 섞이는 것**이 가장 큰
위험이다 — 그 순간 표 전체의 신뢰도가 가장 약한 행까지 내려간다.

그래서 전수를 이렇게 정의한다:

> **모든 행에 판정이 붙는다. 그리고 행마다 그 판정이 기계 근거인지 소스 인용인지가 남는다.**

"전부 LLM 이 읽는다"가 아니다. 층마다 결론을 내는 방식이 다르고, 각 층은 **자기가 결론을 못
내면 그렇게 말한다.** 침묵은 통과가 아니다.

---

## 3. 네 개의 층

### 1층 — 모듈-필드 소속 (기계, 전건, 값을 보지 않음)

**질문**: 이 가중치 축에 붙은 이름이 가리키는 config 필드를, 그 모듈이 실제로 읽는가?

파라미터의 shape 은 그것을 소유한 모듈이 **선언**한 것이다. `nn.Linear(a, b)` 의 두 폭은
그 모듈을 만든 코드가 config 에서 읽어 정한 값이다. 그러니 그 모듈도, 그 모듈을 만든 부모도
읽지 않는 필드의 이름이 붙어 있으면 **산술이 아무리 맞아도 근거가 없다.**

이것이 **값을 전혀 보지 않는 유일한 검사**다. 값 충돌은 이 검사에 아무 영향을 못 준다.

- 구현: `src/source_check.py` — `class_config_reads` / `_owner_reads` / `membership_gaps`
- 조인 키: `models/<모델>/full/module_classes.json` (모듈 경로 → 소스 클래스).
  트레이스 때 `run.py` 가 쓰고, 기존 모델은 `develop/backfill_module_classes.py` 가 채운다
  (가중치 없는 meta 빌드 한 번, 모델당 1초 미만)
- 책임 범위는 **자기 클래스 + 그것을 만든 부모 클래스**까지. 루트까지 올라가면 모델 클래스가
  거의 모든 필드를 읽어서 검사가 영원히 발화하지 않는다
- **판정 불가를 통과로 바꾸지 않는다**: 상위 클래스가 다른 파일에 있어 읽는 필드를 다 볼 수
  없는 클래스는 제외 목록에 이름이 남고, 그 축에 대해서는 아무 주장도 하지 않는다

거짓 양성 세 종류는 소스에서 접지해 제거했다 — config 의 `attribute_map` 별칭,
`@property` 로 계산되는 필드(그 재료를 모듈이 읽으면 인정), 그리고 한 심볼이 정당하게 여러
필드를 뜻하는 경우(`d_moe` 는 `moe_intermediate_size` 이자 `shared_expert_intermediate_size` 다).

### 2층 — 형태 불변식 (기계, 전건)

**질문**: 이 shape 이 물리적으로 가능한가?

축의 **순서·중복·공존**은 이름이 무엇이든 독립적으로 판정할 수 있다. 여기서 결론이 나면
LLM 이 볼 필요가 없다.

| 불변식 | 무엇을 잡는가 |
|---|---|
| `batch_excl` | `B` 가 두 번, `T` 뒤에, 가중치 안에 |
| head 상호배제 | `n_h` 와 `n_kv` 는 한 shape 에 공존할 수 없다 |
| 가중치에 `T` 없음 | 파라미터는 seq_len 에 의존할 수 없다 |
| elementwise 라벨 일관성 | 같은 concrete shape 인 피연산자와 출력이 다른 이름을 달 수 없다 |
| reshape 자체 유도 | 한 행 안에서 입력·출력 설명이 서로 모순되는가 |

- 구현: `develop/verify_all.py`
- 3층에서 새 불변식이 발견되면 **여기로 승격한다.** 그것이 이 절차의 산출물이다

### 3층 — 소스 대조 (LLM, 근거 인용 필수)

1·2층이 끝내지 못한 것만 온다. 여기서만 판단이 필요하다.

**작업 단위는 모델 하나 × 절 하나.** 한 번에 여러 모델을 묶지 않는다 — 어떤 변경이 무엇을
고쳤는지 귀속되지 않고, 긴 문서를 이어 읽을수록 뒤쪽이 흐려진다.

**우선순위** (같은 노력이면 여기부터가 발견률이 높다):

1. **B절 — 이름 없는 정수 중 이 모델의 심볼과 값이 같은 것.** 스코프가 그 모듈을 못 덮었다는
   신호다. `n_hc` 가 이렇게 잡혔다
2. **라벨 출처가 약한 축** — `heur_*`, `out_of_scope_symbol`, `reused_symbol`.
   현재 함대에서 이 셋을 합쳐 **2.24%** (heur 0.20% / out-of-scope 0.01% / reuse 2.04%)
3. **A절 — 붙은 이름 × 모듈** 전건. 그 모듈에서 그 이름이 말이 되는가
4. **C절 — 모듈별 출력 shape** 전건. 어떤 모듈에 **있을 수 없는 이름**이 섞여 있는가

**증거 요건** — 아래가 없으면 판정이 아니다:

- 클래스·메서드 이름
- **인용한 코드 줄** (파일:줄 번호)
- HF 소스로 부족했다면 무엇을 더 봤는지 URL

**출처 사다리** (권고 순서지 울타리가 아니다):

> `develop/sources/modeling_*.py` → config 클래스 docstring → 모델 저장소 remote code →
> vLLM / SGLang / TRT-LLM → 커널 저장소 → 논문 → model card·블로그 → 검색

커스텀 커널(Triton/CUDA — KDA, mamba-ssm, causal-conv1d, flash-attn)은 HF 에 torch fallback 만
있고 **우리 트레이스도 그 fallback 을 돈 것**이므로 실제 커널과 shape 이 다를 수 있다. 그럴 땐
사다리를 내려간다.

**이전 판정 이월** — 시작 전에 `models/<모델>/review_findings.json` 을 먼저 읽는다. 이미
`current_label_correct` 로 종결된 질문은 다시 묻지 않는다. 다시 물어야 한다면 그건 산출물이
바뀌었다는 뜻이고, 원장이 이미 **만료**로 표시해 둔다.

### 3층 보강 — 자기 산출물을 믿지 않는다

외부 검토(2026-08-12)가 우리 절차의 구멍을 정확히 짚었다. **`model_summary.md` 나
`review_findings.md` 같은 자체 산출물은 참고일 뿐, 그 자체가 검증이 아니다.** 그때 이렇게
드러났다 — 세 모델이 원장에 "최신"으로 찍혀 있었는데 실제로는 의뢰서의 질문에 답하지
않았고(Llama-3.1-405B 는 "의뢰서가 비어 있었다"고 사실과 다르게 적혀 있었다),
`ambiguous.json` 의 `chosen` 필드는 **전 모델 전 행이 비어 있었다**.

그래서 셋을 기계 검사로 내렸다:

| 검사 | 무엇을 막는가 |
|---|---|
| `unanswered` | 의뢰서가 질문 N건을 냈는데 판정이 0건이면 게이트 FAIL |
| `stale` | 산출물이 현재 `rules/`+`src/` 로 만들어졌는지 지문 대조 |
| `override_dead` | 반영했다고 적힌 교정이 실제로는 한 축도 안 바꿨으면 FAIL |

**보고서가 아니라 산출물 자체를 재세어 확인한다.** 검토자에게도 같은 것을 요구한다 — 우리
체크리스트를 읽지 말고 `full/*.csv` 와 `*.jsonl` 을 직접 세라.

### 3층 보강 — 접힌 표는 한 줄도 빠짐없이 훑는다

A/B/C 절은 (모듈, 라벨) 단위로 접은 뷰다. 그 접기가 못 보는 것이 있다: **한 행 안에서
필드끼리 어긋나는 것.** 외부 검토가 `prefill.jsonl` / `decode.jsonl`(주요 op 만 담은 접힌 표,
모델당 수백 줄)을 **샘플링 없이** 순회해 `weight_shape` 와 `input_shape` 의 같은 텐서가 다른
이름을 쓰는 것을 찾아냈다 — 함대 4,406건이었고 우리 검사 어느 것도 볼 수 없었다.

이제 그 부류는 `weight_operand` 불변식으로 기계가 잡는다. 하지만 **원칙은 남는다**: 접힌 표는
읽을 수 있는 크기이니 한 줄씩 읽어라. 한 행 안의 `input_shape` / `weight_shape` /
`output_shape` 가 서로 말이 되는지가 접힌 뷰에서는 보이지 않는다.

### 4층 — 커버리지 회계 (기계)

각 모델의 `review_findings.json` 은 **어느 절을 수행했는지**를 `angle` 에 기록하고, 원장
(`develop/verify/review_ledger.yaml`)이 산출물 지문과 함께 보관한다. 산출물이 바뀌면 자동으로
만료되어 다시 올라온다.

**안 한 것과 깨끗한 것은 구별된다.** "C절 미수행" 은 정직한 기록이지 흠이 아니다. 흠은 안 한
것을 한 것처럼 적는 것이다.

## 4. 판정과 그 뒤

| 판정 | 뜻 | `status` |
|---|---|---|
| `current_label_correct` | 안건이 오탐. **왜 오탐인지가 탐지기 개선의 재료다** | `fixed` |
| `should_be_renamed` | 교정 대상. 제안 이름 + 근거 줄 | 고쳤으면 `fixed`, 못 박았으면 `open` |
| `no_name_exists` | 루프 인덱스·피연산자 개수. **정수로 두는 것이 정답** | `fixed` |
| `undetermined` | 소스에 근거가 없다. **무엇을 봤고 뭐가 없었는지 적는다** | `open` |

**멈춤 규칙**: 사다리를 끝까지 내려가도 답이 없으면 `undetermined` 로 남기고 **본 곳을 전부
적는다.** 짐작으로 메우지 않는다. 값이 맞는다는 이유로 이름을 짓지 않는다(P1).

**승격이 진짜 성과다.** 문서에만 남기면 다음 모델에서 똑같이 반복된다 — `01-procedure.md` 5절.
특히 **오탐이 나오면 탐지기를 고친다.** 정사각 행렬 예외 하나로 조사 대상이 52,687축 →
1,752축이 됐다.

## 5. 이 절차가 살아 있는지 확인하는 법

검사를 믿으려면 검사가 죽지 않았다는 증거가 있어야 한다. `develop/verify_selftest.py` 는
검사마다 고장을 주입해 실제로 잡히는지 확인한다(현재 21/21). 2층에 불변식을 추가할 때는
**폴트 인젝션도 같이 추가한다.** 리뷰 패킷도 같은 시험에서 1/4 로 떨어진 적이 있고, decode 와
shape 별 표본을 넣고 나서야 통과했다.

## 6. 1회차 실적 (2026-08-11)

1층을 새로 도입해 함대를 훑은 결과 — 전부 **값으로는 절대 구별할 수 없는** 것들이었다:

| 모델 | 축 | 렌더된 이름 | 소스가 말하는 것 |
|---|---|---|---|
| DeepSeek-V4 (3종) | `indexer.scorer.weights_proj` 출력 | `n_h` | `index_n_heads` — `nn.Linear(hidden_size, config.index_n_heads)` (modeling_deepseek_v4.py:444) |
| DeepSeek-V4 (3종) | `indexer.kv_proj` / `gate_proj` 출력 | `d_head/2` | `2*index_head_dim` (:489) |
| DeepSeek-V4 (3종) | `indexer.q_b_proj` 출력 | `g_o*d_g` | `index_n_heads * index_head_dim` (:494) |
| DeepSeek-V4 (3종) | `indexer` 입력 | `n_h*d_head/g_o`, `n_h*d_rope` | `d_model` — 둘 다 4096 으로 잔차 폭과 겹쳤다 |
| Nemotron-3 Super/Ultra | `shared_experts` 폭 | `d_moe` (필드 미접지) | `moe_shared_expert_intermediate_size` (modeling_nemotron_h.py:689) |

원인은 하나다: **스코프 정규식이 경로 어디서든 매치한다.** `indexer` 는 `self_attn` 안에 있어
바깥 모듈의 스코프를 물려받았고, `index_n_heads == num_attention_heads == 64` 라 값으로는
아무것도 드러나지 않았다. 이제 **더 안쪽 스코프가 이긴다**(`symbolic_shape._ctx_symbols`).

게이트: `퇴행 0 / 개선 4`, 셀프테스트 21/21, 1층 위반 **0건**.
