# T 선택이 아키텍처 제약을 안 봅니다 — V4-Pro 에서 드러났습니다

## 1. 진행 상황

지시하신 절차대로 4개 모델을 비퇴화 배치(B=3)로 돌리고 있습니다.

```
Llama-4-Maverick   승인   게이트 FAIL 0 / 독립 배치(B=4) pass / 사람이 볼 것 0
gpt-oss-20b        승인   동일
gpt-oss-120b       승인   동일
DeepSeek-V4-Pro    보류   <- 아래
Kimi-K3            진행 중
```

전환 diff·독립 배치 검증·`audit_manifest` 게이트는 다 붙였고 자기검사도 통과합니다
(manifest 없음 / 미승인 / 검사 뒤 변조 / manifest 자기해시 — 4/4 거부 확인).

도중에 프로브 결함도 하나 잡았습니다: 검증 트레이스가 `run_once()` 를 직접 불러
**적응 재시도 경로를 건너뛰었습니다.** gpt-oss 의 MoE `grouped_mm` 은 bf16 이 아니면 죽어서
발행본은 되는데 검증만 실패했습니다.

## 2. V4-Pro 에서 나온 문제

`resolve_capture_sizes` 가 `(B, T)` 를 함께 고르면서 **T 가 2048 -> 2049** 로 바뀌었습니다
(Llama-4·gpt-oss 는 그대로).

### 좋아진 것

옛 T=2048 에서 `T/m_csa = 2048/4 = 512 = d_head` 가 충돌해 `T/m_csa` 로 오라벨된 축
**2,250개**가 `d_head` 로 바로잡혔습니다.

### 나빠진 것

`compressor` 와 `indexer` 의 시퀀스 축이 이렇게 됐습니다.

```
옛(T=2048)  [B, T,        d_head]        [B, T,      2*c_I]
새(T=2049)  [B, 4*d_head, d_head]        [B, 2*k_I,  2*c_I]
                 ^^^^^^^^                     ^^^^^
```

그 축의 구체값은 새 트레이스에서도 **2048** 입니다. compressor 가 시퀀스를 `m_csa=4` 의
배수로 내림하기 때문으로 보입니다(`rules/derived_dims.yaml` 에 `T // m_csa` 는 등록돼
있지만 `m_csa * (T // m_csa)` 는 없습니다).

즉 옛 T 에서는 2048 이 4의 배수라 축이 T 와 **정확히 같았고**, 새 T 에서는 갈라져
2048 과 값이 같은 곱(`4*d_head` = 4×512, `2*k_I` = 2×1024)이 지어진 것입니다.

**`runtime_role_change` 범주가 이걸 잡았습니다**(182건). 만들라고 하신 그 범주입니다.

## 3. 기존 기제로는 안 됩니다

`introspect.derive_min_seq_len` 은 **최솟값만** 정하고(상한 2048) 나눠떨어짐은 안 봅니다.
KDA 의 `T % 64 == 0` 은 프로필에 `seq_len` 을 손으로 박아 해결했습니다(Kimi-K3).

## 질문

**Q1 (T 선택에 나눠떨어짐 제약).** `resolve_capture_sizes` 가 아키텍처 제약을 봐야 합니까?
본다면 제수를 어디서 얻습니까?

  (a) config 필드 이름으로 추정 -- chunk/window/group 계열 값들의 최소공배수
  (b) 프로필에 `seq_len_multiple_of` 를 두고 모델별로 적는다(KDA 처럼 손으로)
  (c) 트레이스로 발견 -- 두 T 로 돌려 "T 를 따라가지만 T 와 다른" 축이 있으면 그 비율에서
      제수를 역산

(c)가 근거로는 제일 강해 보이는데 트레이스를 한 번 더 돌려야 합니다. (a)는 이름 추정이라
이 저장소가 싫어하는 방식이고, (b)는 모델마다 손이 갑니다.

**Q2 (내림 식을 등록).** 대안으로 `m_csa * (T // m_csa)` 같은 **내림 식**을 유도 규칙에
등록하면 T 가 무엇이든 그 축이 이름을 얻습니다. 다만 이런 식을 일반으로 열면 값이 맞는
아무 곱이나 붙을 위험이 커 보입니다. 어느 쪽이 맞습니까?

**Q3 (T 를 아예 안 바꾸는 선택지).** `resolve_capture_sizes` 가 `resolve_seq_len` 이 고른 T 를
**우선 유지**하고 B 만 바꾸게 하면, V4-Pro 는 T=2048 그대로라 이 문제가 안 생깁니다. 대신
`T/m_csa = d_head` 충돌 2,250건이 남습니다. 둘 다 잡으려면 T 는 **`m_csa` 의 배수이면서
`T/m_csa != d_head`** 여야 합니다(예: 2052). 그게 Q1 (b)/(c) 로 가는 길로 보이는데 맞습니까?

**Q4 (V4-Pro 를 지금 어떻게 합니까).** 남은 검토 대상은 `semantic_change` 2,250(위 개선),
`semantic_topology_change` 2,126(`unbind`/`alias`/`slice`/`cat` -- 아직 안 봤습니다),
`runtime_role_change` 182(위 퇴행)입니다. T 문제를 먼저 풀고 재생성하는 것이 맞습니까,
아니면 지금 판으로 나머지를 먼저 검토합니까?
