# 방향 전환을 검토해 주세요 — **모르는 축은 이름을 붙이지 않는다**

지금까지와 다른 제안입니다. 구현 전에 방향 자체를 봐 주시면 좋겠습니다.

## 무엇을 바꾸려는가

지금 파이프라인은 **값이 겹쳐 고를 근거가 없을 때도 이름을 붙입니다.** 전역 우선순위,
즉 관례로 하나를 고릅니다. 그 축이 **465,213개**입니다(47개 모델, 전체 축의 3.7%).

바꾸려는 것: 그런 자리는 **미결로 남기고**, 그 목록을 LLM 판정 층으로 넘깁니다.

## 왜 — 지난 7라운드가 같은 벽에 부딪혔습니다

지적해 주신 오라벨은 거의 전부 이 46만 축에서 나왔습니다. 그런데 고치는 것이 매번
"수정"이 아니라 **"충돌"** 이었습니다:

```
값이 겹침 -> 관례로 하나 고름 -> 등가류가 그 이름을 퍼뜨림
-> 소스로 확정한 이름을 넣으려니 클래스가 쪼개짐 -> 충돌 -> 되돌림
```

실측한 되돌림들:

| 시도 | 결과 |
|---|---|
| head <-> state 맞바꿈 교정(Granite/Nemotron) | 등가류 충돌 0 -> **887** |
| 교정 뒤 전치 불변식 재적용 | Kimi-K3 전치 261->168, 그러나 충돌 0 -> **117** |
| Qwen3-Next conv_dim 교정 | 전치 위반 0 -> **72** |
| Llama-4 `E -> E*B` | 충돌 0 -> **24** |

전부 "결함을 다른 결함으로 바꾸는 거래"라 되돌렸습니다. 핵심 지표는 라운드 5·6·7 내내
**그대로**였습니다(전치 277 / 이름생성 351 / reshape 474).

**틀린 이름이 이미 확정된 것처럼 자리를 잡고 있는 것**이 문제라고 봅니다. 빈칸이었다면
채우는 일이었을 것을, 지금은 자리싸움을 해야 합니다.

## 질문 1 — 방향 자체가 맞습니까

산출물은 당장 나빠 **보입니다**. 46만 축이 이름을 잃고 `bare` 비율이 오릅니다.
표를 읽는 사람에게는 "전보다 모르는 게 많아졌다"로 보입니다.

저희 판단은 "지금 그 46만은 **맞는지 아무도 모르는 이름**이므로 정직한 빈칸이 낫다" 입니다.
동의하십니까? 아니면 이 3.7% 를 잃는 대가가 너무 큽니까?

특히 걱정되는 것: **미결이 연쇄로 번지지 않겠습니까?** 지금은 등가류가 관례로 고른 이름을
퍼뜨려 주변 축까지 채웁니다. 미결로 두면 그 축을 통과하는 reshape/matmul 의 유도도 끊겨
3.7% 보다 훨씬 많이 비어질 수 있습니다. 저희는 shadow 로 먼저 재려 하는데, 그 수가 얼마면
"너무 많다"로 봐야 합니까?

## 질문 2 — 표기 방식

세 후보를 생각했습니다.

| 표기 | 장점 | 단점 |
|---|---|---|
| `?` | 가장 정직 | 정보 0 |
| `128`(구체 정수) | 크기는 알 수 있음 | 지금의 `bare` 와 구분 안 됨 |
| `?d_head\|n_h` | 후보를 보여줌. LLM 질문과 1:1 대응 | 표가 지저분해짐, 파서 영향 |

저희는 세 번째로 기울었습니다 — 표만 보고도 "둘 중 하나인데 확정 못 했다"가 읽히고,
답이 들어오면 그 자리를 정확히 추적할 수 있습니다. 다만 `<phase>.csv` 는 지금 기계가 읽는
산출물이기도 해서 스키마 영향이 걱정됩니다. 어느 쪽을 권하십니까?

지금 이미 있는 것과의 관계도 정리가 필요합니다:
- `bare` — 이름을 못 붙였고 크기가 커서 진짜 차원일 수 있는 축(현재 6.5%)
- `heur_*` — 등록 규칙이 없어 산술로 지어낸 이름(0.1%)
- 새로 생길 `tie 미결`
셋을 한 표기로 합쳐야 합니까, 구분해야 합니까?

## 질문 3 — LLM 층 연결

지금도 `models/<model>/review_request.md` 가 질문을 냅니다. 문제는 **답을 안 해도 표에는
이미 이름이 박혀 있다**는 것입니다. 그래서 검토가 "빈칸 채우기"가 아니라 "이미 박힌 이름이
틀렸음을 증명하기"가 됩니다 — 매번 반박 프레임으로 일하셔야 했던 이유입니다.

비워두면 뒤집힙니다. 질문 파일을 이렇게 자동 생성하려 합니다:

```yaml
- id: qwen35-397b-linear_attn-64
  model: Qwen__Qwen3.5-397B-A17B
  module: model.layers.*.linear_attn
  value: 64
  candidates: [d_chunk, n_h_lin_v]
  axes: 106429
  anchor_shape: "[B, T, ?, d_head_lin_v]"      # 위치가 단서다
  source_file: develop/sources/modeling_qwen3_5.py
  evidence_rows:                                # 실제 트레이스 행 표본
    - "view [[B, T, 2*d_k_lin+d_v_lin]] -> [[B, T, ?, d_head_lin_v]]"
  answer:                                       # <- LLM 이 채운다
  source_quote:                                 # <- 근거 줄 인용 (없으면 거부)
```

여쭙고 싶은 것:

1. **이 형식이면 답하기 좋습니까?** 무엇이 더 있어야 판정이 됩니까? 지금 저희가 주는
   `full/review.md`(shape 별 행 표본), `structure.yaml`(심볼 표), `<phase>.csv` 중
   실제로 쓰시는 것은 무엇입니까?
2. **한 질문에 몇 축까지 묶어도 됩니까?** `d_chunk vs n_h_lin_v` 는 10만 축을 한 질문으로
   접은 것입니다. 이렇게 크게 접으면 "그 모듈의 그 값은 전부 같은 축"이라는 가정이 들어가는데,
   그 가정이 깨지는 경우를 보신 적이 있습니까?
3. **답을 어떻게 받는 것이 안전합니까?** 지금은 사람이 `rules/label_overrides.yaml` 에
   옮겨 적습니다. 답 파일을 그대로 읽어 반영하려 하는데, `source_quote` 가 실제 소스에
   존재하는지 기계로 검증하는 것 말고 무엇을 더 걸어야 합니까?
4. **미결로 남는 것이 정답인 경우**(출신으로만 구별되고 소스에도 근거가 없는 자리)를
   어떻게 표시하는 것이 좋습니까? 지금은 `status: open` 으로 두는데, 그러면 매 재생성마다
   같은 질문이 다시 올라옵니다.
