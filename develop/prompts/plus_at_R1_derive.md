# R1 — 축의 의미를 **직접 도출**해 주십시오 (blind)

요청일 2026-09-27. 이 라운드는 `develop/PLAN_plus_at_layer.md` v3 의 R1 입니다.

---

## 이 라운드의 규칙

이 문서에는 **제가 제안한 이름과 식이 들어 있지 않습니다.** 후보 목록도 드리지 않습니다 --
후보를 주면 거짓 양자택일과 anchoring 이 생긴다는 지적을 받아 그렇게 설계했습니다.

그래서 부탁드리는 것은 하나입니다.

> **발행본에 맨 정수로 남은 축들이 각각 무엇인지, 소스를 읽어 직접 판정해 주십시오.**

판정이 서지 않는 자리는 `cannot determine` 으로 두시면 됩니다. 그게 정답인 자리도 있습니다.

## 배경 (판정에 필요한 만큼만)

`llm-arch-tracer` 가 Kimi-K3 를 트레이스해 op 단위 표(`prefill.csv` / `decode.csv` 와 같은
내용의 jsonl)를 냈습니다. 각 행은 한 op 이고 `input_shape` / `weight_shape` /
`output_shape` 의 축은 심볼로 렌더됩니다. 예: `[[B, T, d_model]]`.

**일부 축은 심볼을 못 받고 맨 정수로 남았습니다.** 사용자는 이 표의 심볼에 값을 대입해
roofline 과 DAG 를 만들고 **배치 크기와 config 를 스윕**하려고 합니다. 그래서 맨 정수는
"값이 맞다" 로 끝나지 않습니다 -- 스윕하면 틀립니다.

읽을 데이터는 별첨 `plus_at_R1_data.md` 입니다. 거기에 있는 것:

```
트레이서가 낸 심볼표            (B=3, T=320, k=16, d_chunk=64, E=896, ...)
config 발췌                     (attn_res_block_size, linear_attn_config, num_experts, ...)
트레이스 대체 기록 adaptation_log (어떤 계산이 대체됐는지와 그 caveat 원문)
맨 정수가 든 shape 패턴 전수      prefill 37 종 / decode 36 종
대표 자리의 이웃 문맥            depends_on 으로 앞뒤를 따라간 op 사슬
```

## 물어보는 것

### Q1. 각 맨 정수 축이 무엇입니까

별첨의 shape 패턴 목록을 보시고, 자리 수가 많은 것부터 다음을 적어 주십시오.

```
shape 패턴과 축 위치
그 축의 의미            (무엇을 세는 축인가)
식                      (다른 심볼로 표현되는가. 안 되면 그렇게 적어 주십시오)
근거                    파일:줄 + 그 줄이 왜 그 결론을 지지하는가
유효 조건               그 식이 성립하려면 무엇이 참이어야 하는가
아키텍처인가 트레이스 산물인가
```

특히 갈라 주셔야 하는 것: **모델의 속성인 축**과 **이 트레이스가 만든 축**입니다. 후자는
표에 아키텍처 심볼처럼 적으면 읽는 쪽이 오해합니다.

### Q2. 어디까지 바꿔야 합니까 (footprint 독립 도출)

식을 붙이기로 판정한 축에 대해, **발행본의 어느 셀들이 바뀌어야 하는지** 규칙으로 적어
주십시오. 제 선택자 결과는 보여드리지 않았습니다 -- 독립적으로 도출해 주시는 것이 이
라운드의 핵심입니다.

```
선택 규칙       module / op_type / shape / field / shape_index / axis 중 무엇으로 고르는가
예상 셀 수      그 규칙이 덮는 자리 수 (별첨의 패턴별 자리 수로 계산 가능합니다)
바뀌면 안 되는 자리  같은 값이 다른 뜻으로 쓰인 자리가 있으면 지목해 주십시오
```

세 번째가 중요합니다. 같은 정수가 한 모델 안에서 여러 뜻으로 쓰이는 경우, 값만 보고 바꾸면
맞는 자리를 망칩니다.

### Q3. 바꾸지 말아야 할 축이 있습니까

전부 심볼로 만드는 것이 목표가 아닙니다. **리터럴이 맞는 축**이 있으면 그렇게 적어
주십시오. 판단 기준도 함께 주시면 좋겠습니다.

### Q4. 표 자체에 모순이 있습니까

발행본을 직접 열어 보실 수 있습니다. 같은 축이 자리에 따라 다르게 렌더된 곳이 있는지,
또는 어떤 축의 이름이 그 op 의 정의와 안 맞는 곳이 있는지 짚어 주십시오.

## 형식

답을 아래처럼 주시면 제 판정과 대조해 기록에 남기겠습니다.

```
축 1
  shape/축      [...] 의 축 N
  의미          ...
  식            ... | cannot determine
  근거          파일:줄 -- 왜
  유효 조건     ...
  분류          architecture | trace_artifact | literal_is_correct
  footprint     선택 규칙 + 예상 셀 수 + 바뀌면 안 되는 자리
```

## 마지막으로

제 판정은 이 라운드가 끝난 뒤에 공개하고, 두 판정이 갈리면 **양쪽을 다 싣고 미해결로
표시**합니다. 그러니 제 결론에 맞추려 하지 말아 주십시오 -- 갈리는 것이 이 라운드의 산출물
중 하나입니다.

`cannot determine` 을 쓰는 것이 억지 판정보다 낫습니다.
