# 정직한 빈칸 + LLM 채움 — 일반 기제로 만들고, 4개 모델부터 쓴다

목표: **gpt-oss / Llama-4-Maverick / Kimi-K3 / DeepSeek-V4-Pro** 의 `prefill|decode.csv|jsonl`
축 라벨을 근거 있는 상태로 만든다.

## 원칙 두 가지 (2026-09-10 사용자 지시)

1. **4개 모델 전용 변경을 만들지 않는다.** tracer 업그레이드는 나중에 이어서 하므로, 지금
   넣는 것은 전부 **일반 기제**여야 한다. 모델별 지식은 코드가 아니라 `rules/` 의 데이터로만
   들어간다(`label_overrides.yaml`, `references.yaml`). 이 4개는 그 기제의 **첫 사용자**이지
   변경 범위가 아니다.
2. **모르는 것은 빈칸으로 둔다.** 규칙이 못 정한 축을 지금처럼 조용히 하나 골라 채우지 않고,
   비운 채로 질문을 만들어 LLM 이 채우게 한다.

## 왜 빈칸이 가능한가 — 실측

리졸버는 **자기가 임의로 골랐다는 것을 이미 알고 있다.** `src/symbolic_shape.py:371` 의
`_pick()` 은 같은 값을 가진 후보가 둘 이상이면 전역 우선순위로 하나를 고르고 그 사실을
`ties` 에 적는다.

```python
if len(ms) > 1:
    ties[(module_path or "", n, tuple(sorted(ms)))] += 1
return ms[0]          # <- 우선순위는 관례이지 근거가 아니다
```

함대 전체:

```
임의 선택 축 465,213 (전체의 3.7%)  ->  질문 120개 / 모델 30개
   122,496축  6질문  Qwen3.5-397B-A17B
    27,282축  9질문  DeepSeek-V4-Pro
    25,364축 12질문  DeepSeek-V4-Flash(-0731)
    21,824축  3질문  Nemotron-3-Super
    17,892축  1질문  Llama-3.1-405B
```

**빈칸으로 바꿔도 물어볼 것은 120개뿐이다.** 같은 `(모듈, 값, 후보들)` 질문 하나가 수천 축을
덮기 때문이다. 이것이 이 설계가 성립하는 이유다.

## 0순위 — 증거가 재트레이스마다 지워진다

`develop/promote.py:39` 가 `shutil.rmtree(dest)` 로 모델 디렉터리를 통째로 지운다.
`review_findings.json` 은 ③층이 쓰는 파일이고 트레이스가 재생성하지 않으므로 **promote 마다
사라진다.** 47/47 에서 없어져 있었다(복구 커밋 다음 재트레이스에서 또 날아갔다).

교정 적용에 재트레이스가 필수이므로, 이걸 안 고치면 반복할 때마다 증거를 잃는다.
**모델 전용이 아니라 파이프라인의 일반 결함이다.**

## 근거의 우선순위 — 값을 안 보는 것부터

교정은 이 순서로만 만든다. 위에서 답이 나오면 아래는 안 쓴다.

1. 모듈 선언 폭 (`nn.Linear` 의 `in_features/out_features`)
2. 모듈-필드 멤버십 (그 모듈이 실제로 읽는 config 필드에서만 이름이 나온다)
3. 소스 대조 — 실행된 `transformers` **설치본** 기준
4. 다중 길이 프로브 — T 유도 충돌만. config 상수 충돌에는 무력하다
5. **LLM 판정** — 위 넷으로 안 되는 것
6. ③ 자유 평가 — 규칙이 못 보는 오류

## LLM 판정 계약

* 질문 하나 = **`(module_key, value, candidates)` 하나**. 수천 축이 한 답으로 채워진다.
* 프롬프트에 담는 것: 모듈 경로, op, 심볼·구체 shape, 그 모듈이 읽는 config 필드와 값,
  소스 조각, 후보 이름들, 그리고 **그 축이 나타나는 자리들의 예시**.
* 답에 반드시: ① 확정 이름 ② **소스의 어느 줄** ③ **반증 조건**.
* 셋 중 하나라도 없으면 채택하지 않고 **빈칸으로 남긴다.** "값이 맞는다" 는 근거가 아니다.
* 인용한 줄을 **실제 파일에서 다시 읽어 문자열 일치를 기계적으로 확인**한다.
* 채택분만 `rules/label_overrides.yaml` 에 `source:` 를 달아 넣고, **Codex 가 독립으로 같은
  소스 줄을 짚어야** 통과시킨다.

## 반복 절차 (모델 하나당)

```
a 질문 묶음 생성 -> b 판정(소스 -> LLM) -> c 교차검증 -> d 교정 적용(재트레이스+promote)
-> e 게이트(verify_all exit 0) -> f ③ 자유 평가 -> g 남은 건 빈칸 + 사유 기록
```

`d` 는 재트레이스가 필수다. `regen_tables.py` 로는 교정이 구조적으로 발화하지 않는다.
