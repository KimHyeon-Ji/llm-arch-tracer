# 근본 원인을 다시 봅니다 — B=1 로 트레이스하는 것 자체가 문제 아닙니까

`b_dep` 을 구현하다 멈췄습니다. 절반은 되는데 **같은 축에 두 이름이 나옵니다**. 그런데
멈춰서 보니, 지금까지 고친 것들이 전부 한 뿌리에서 나온 것 같습니다.

## 1. 이 저장소는 이미 같은 문제를 T 에 대해 풀었습니다

`src/symbolic_shape.py:122` `resolve_seq_len`:

> config 값이나 순수 config 유도값과 **하나도 겹치지 않는 가장 작은 seq_len** 을 고른다.
> 외부 검토(2026-07-29)가 Llama-3.1-405B 의 T=16 이 GQA 반복 계수 `n_h/n_kv = 128/8 = 16`
> 과 정확히 같아 여러 활성 축을 반복 계수 식으로 오라벨한 것을 찾은 뒤 넣었다.

즉 **"한 번의 실행으로는 같은 숫자를 구분할 수 없으니, 애초에 겹치지 않는 크기를 고른다"**
가 이 프로젝트의 답이었습니다.

**그런데 배치는 1 로 박혀 있습니다**(`src/inputs.py` 의 `.view(1, -1)`). 고를 수 있는 값 중
가장 나쁜 것입니다 -- 모든 싱글턴과 같고, 모든 곱에서 사라집니다.

## 2. 이번에 고친 것들이 전부 그 결과입니다

```
decode 의 가짜 `B`              [40,1,128] 의 가운데 1 이 배치인지 query 길이인지 모름
접힌 배치 누락 prefill 2,945    B*n_h == n_h, B*T == T 라 값으로 못 가름
방송 싱글턴을 `B` 로 61축        크기 1 이면 전부 배치로 보임
spread:class 쪼갬 192           위를 한쪽만 고쳐서 생김
```

`b_dep` 기계장치도, B=2 프로브도, 배치 축 불변식도 전부 **B=1 때문에 잃은 정보를 되찾는
장치**입니다. 안 잃으면 필요 없습니다.

## 3. 제안 — 기본 트레이스를 충돌 없는 B 로

`resolve_seq_len` 과 같은 방식으로 `resolve_batch(cfg)` 를 두고, config 값·유도값과 겹치지
않는 가장 작은 `B >= 2` 를 고릅니다. 그러면:

```
B = 3 일 때
  배치 축      3        방송 싱글턴 1        -> 다르다
  B*n_h = 120  n_h = 40                      -> 다르다
  B*T = 51     T = 17                        -> 다르다
  E*B = 384    E = 128                       -> 다르다
```

값 기반 라벨링이 **그냥 맞습니다.** `b_dep`, B=2 프로브, 배치 불변식, decode 의 scoped
override 가 전부 필요 없어집니다.

### 확인한 것

* B>1 트레이스는 이미 됩니다. `src/inputs.py` 에 `batch` 인자를 열어 B=2 로 prefill/decode
  를 모두 돌렸습니다(Llama-4, meta 백엔드).
* 비용은 큽니다: 47개 전량 재트레이스. 다만 meta 텐서라 shape 전파뿐이라 시간은 선형입니다.
* B>1 에서 **op 구성이 조금 달라집니다**. 메모리 연속성 때문에 `view` 가
  `clone` + `_unsafe_view` 로 갈리는 자리가 있습니다(Llama-4 prefill 972 op, decode 120 op).
  이건 실제 동작이고 B=1 쪽이 오히려 특수한 경우로 보입니다.
* MoE 라우팅은 배치에 따라 전문가별 토큰 수가 달라집니다. 한 번만 트레이스하면 문제가
  아니지만, `tdep`(prefill/decode 대조)의 짝짓기에는 영향이 있을 수 있습니다.

고르는 편이 낫습니까?
