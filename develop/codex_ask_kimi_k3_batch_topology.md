# 질문 — Kimi-K3 의 B=1 vs B=3 전환 diff 를 어떻게 판정해야 합니까

## 상황 요약

이 저장소는 발행 트레이스를 **B=1 에서 B=3 으로** 바꿨습니다. B=1 에서는 배치·decode 쿼리
길이·방송 싱글턴이 수치적으로 같고 `B*T == T`, `B*n_h == n_h` 라 접힌 배치 축이 라벨에서
통째로 사라지기 때문입니다.

네 모델(Llama-4-Maverick, gpt-oss-20b/120b, DeepSeek-V4-Pro)은 전환 diff **0** 으로 통과해
이미 출고했습니다. **Kimi-K3 만** 사람 검토 376,428건이 남았고, 그중 절대다수가
`semantic_topology_change`(= 짝을 못 지은 op 구간) 입니다.

## 먼저 원인을 갈랐습니다

`run.py --batch` 와 `transition_diff --old` 를 추가해 **같은 규칙으로 B 만 바꾼 판**을 하나
더 뜨고 두 비교를 분리했습니다. T 는 세 판 모두 320 으로 동일합니다.

| 비교 | 사람 검토 |
|---|---:|
| 규칙 변화만 (옛 발행본 B=1 ↔ 현재 규칙 B=1) | 3,114 |
| **배치 변화만** (현재 규칙 B=1 ↔ 현재 규칙 B=3) | **376,428** |

즉 8일치 규칙 변화는 거의 영향이 없고 **전부 배치 때문**입니다.

## 확인된 사실

`model.layers.0.self_attn`(KDA 층) 기준입니다. 두 트레이스의 op 구성은 **완전히 같습니다**:

* raw_op 종류 30개, 개수가 30/30 모두 일치
* 모듈 op 수 양쪽 8,749
* 그런데 서명 기반 짝짓기에서 **2,700개가 안 맞습니다**

짝을 못 지은 서명입니다. **shape 은 B=1 좌표로 정규화한 값**입니다(새 판 라벨을 B=1 로
평가 — 그래서 옛 판과 같은 좌표가 되어야 합니다):

```
B=1 에만                                          B=3 에만
320 permute (1,96,1,128)  -> (96,1,128,1)        320 permute (1,96,64,128) -> (1,96,64,128)
320 view    (96,1,128,1)  -> (96,1,128)          320 view    (1,96,64,128) -> (96,64,128)
320 permute (1,96,64,128) -> (96,128,64,1)       320 permute (1,96,1,128)  -> (1,96,128,1)
320 view    (96,128,64,1) -> (96,128,64)         320 view    (1,96,128,1)  -> (96,128,1)
320 bmm     (96,1,128)×(96,128,64) -> (96,1,64)  320 bmm     (96,64,128)×(96,128,1) -> (96,64,1)
320 view    (96,1,64)     -> (96,1,1,64)         320 view    (96,64,1)     -> (1,96,64,1)
```

**bmm 이 서로 전치입니다.** `(96,1,128)×(96,128,64) -> (96,1,64)` 와
`(96,64,128)×(96,128,1) -> (96,64,1)` 는 같은 계산을 피연산자 순서·레이아웃만 바꿔 한 것으로
보입니다. 그 앞뒤의 permute/view 도 그에 맞춰 다릅니다.

해당 소스는 `fla/ops/kda/naive.py:106-150` 의 `naive_chunk_kda` 이고, 문제의 자리는
`A[..., i] = torch.einsum('... c d, ... d -> ... c', k * (g - g_i).exp(), k_i)` 근처로
보입니다(`for i in range(BT)`, BT=chunk_size=64). einsum 이 앞쪽 차원을 접어 bmm 으로
내려갈 때 B=1 과 B=3 에서 접는 방식·피연산자 배치가 달라지는 것으로 추정합니다.

라벨 자체는 양쪽 다 맞는 것으로 보입니다 — B=1 은 `n_h_kda`(96), B=3 은 `B*n_h_kda`(288).

## 이미 고친 것 하나

접힌 `B*n_h_kda`(=3·96=288)가 값이 같은 `n_h+2*n_kv`(=288, fused QKV head 총수)로 나가고
있었습니다. K3 의 KDA 는 q/k/v 가 분리돼 있어 fused QKV 자체가 없는데, 그 유도식의 스코프
정규식이 `attn` 전반을 덮어 걸렸습니다. 해결기에서 **접힌 배치를 스코프 식보다 먼저** 보게
고쳤고, 발행된 B>1 모델 4개의 shape 75,712개를 전부 다시 렌더해 대조한 결과 **바뀌는 축
0건**이었습니다. 이 수정으로 386,790 → 376,428 (10,362건) 줄었습니다.

## 헛짚은 시도 두 번 (참고)

1. `n_chunk`(=T//d_chunk=5)를 유도식으로 등록 → 값 매칭이라 크기 5인 축을 전부 집어삼켜
   `n_chunk` 축이 1,380 → 337,755, 사람 검토 388,584 → 701,154. 물렀습니다.
2. 그 등록이 충돌 회피를 건드려 T 가 320 → 704 로 밀렸고, 청크가 5 → 11 이 되어 op 구성이
   달라지면서 diff 가 1,265,252 까지 갔습니다. 물렀습니다.

## 물어보고 싶은 것

**Q1. 위 bmm 전치는 정말 같은 계산의 다른 lowering 입니까?**
`fla/ops/kda/naive.py` 와 설치된 torch 기준으로, B=1 과 B=3 에서 einsum/matmul 이 왜 다른
피연산자 배치로 내려가는지 확인해 주십시오. 우리 라벨링 결함이 아니라 **PyTorch 의 dispatch
차이**라면 그렇게 판정하고 싶습니다.

**Q2. 그렇다면 전환 diff 는 이 구간을 어떻게 분류해야 합니까?**
지금 `classify_unmatched` 는 구간이 reshape 계열 op 으로만 이루어지고 경계 텐서가 같을 때만
`layout_lowering_verified` 로 승인합니다. 여기는 `bmm` 이 끼어 있고 경계 텐서도 전치라
그 조건을 못 넘습니다. **계산 동치를 어떻게 검증해야 안전합니까?** 예컨대
"구간에 들어오는 텐서 집합과 나가는 텐서 집합이 전치까지 허용해 같고, 원소 수가 보존되며,
파라미터 접근이 같다" 정도면 충분합니까, 아니면 더 필요합니까?

**Q3. 출고 기준을 어디에 둬야 합니까?**
옛 발행본이 B=1 이라 K3 의 전환 diff 는 구조적으로 클 수밖에 없다고 판단하고 있습니다.
대신 **독립 배치 검증**(발행 라벨을 또 다른 배치에서 재평가해 구체 shape 과 대조)을
기준으로 삼는 것이 타당합니까? 지금 돌리는 중입니다. 이게 통과하면 B=3 트레이스가
자기 일관적이라는 뜻이고, 큰 diff 는 결함이 아니라 **공개 사항**으로 다루려 합니다.
이 판단이 맞습니까, 아니면 놓치는 위험이 있습니까?

**Q4. 이 KDA 구간에서 우리가 놓치고 있을 실제 라벨 오류가 있습니까?**
B=3 쪽 라벨(`B*n_h_kda`=288, `d_chunk`=64, `d_head_kda`=128, `n_h_kda*n_chunk`=480 계열)이
`naive_chunk_kda` 의 실제 텐서 의미와 맞는지 소스로 봐 주십시오.
