바뀐 내용:

1. **in-place 덧셈이 표에 다시 실립니다(행 증가의 원인).** "expert bias 가 요약 표에 없다"는
   지적의 원인을 찾으니 범위 선택이 아니라 **선별 코드가 자기 기준과 달랐습니다.**
   `aten.add_.Tensor` 는 op_type 이 `add_` 로 찍히는데 크기 게이트가 `elementwise_add`
   문자열만 봤습니다. 넓은 축(`[B*k*T, d_model]`)을 만지는 덧셈인데 in-place 라는 이유만으로
   빠졌습니다. 함대 실측 294건(gpt-oss-120b 72 / 20b 48, Llama-4 24 등). `clamp` 는 계속
   빠집니다 -- KEEP 목록에 없고 `structure.yaml` 이 그 범위를 밝힙니다.
2. **V4 Indexer 의 nope 폭을 `c_I-d_rope` 로 교정**했습니다(지적하신 네 자리, 각 30축 발화).
3. 그 밖에 라벨 결함 넷을 더 고쳤습니다 -- 아래 "우리가 찾아 고친 것" 참고.

## 우리가 찾아 고친 것 (재검증 부탁드립니다)

전부 B=1 → B=3 전환이 드러낸 값 충돌입니다. 고친 뒤 **발행 4개 모델을 전부 다시 렌더해
바뀌는 축이 0건임을 확인**하고 넘어갔습니다.

| 문제 | 증상 | 조치 |
|---|---|---|
| 접힌 배치가 스코프 식에 짐 | `B*n_h_kda`(288)가 `n_h+2*n_kv`(288)로 | 배치 곱을 스코프 심볼 바로 뒤로 |
| `B*X` 가 아무 축이나 집음 | 청크 슬라이스 12 → `B*d_conv` | 텐서에 배치는 하나 -- 이미 봤으면 시도 자체를 막음 |
| 크기가 배치와 같다고 배치가 아님 | conv cache 3 → `B` → `1` (**산술적으로 거짓**) | 크기가 1일 때만 `1` |
| 개수의 절반은 폭이 아님 | 삼각 루프 인덱스 48 → `n_h_kda/2` | `n_*`/`E`/`k` 는 반 나누기 제외 |

## 검증 상태 (참고 — 이것으로 의미가 맞다고 주장하지 않습니다)

지적해 주신 `check_batch_labels` 의 빈틈 다섯(weight_shape 미검사, zip 이 텐서 개수 차이를
가림, rank 불일치·평가 불가를 통과로 셈, probe 가 낸 phase 만 돎, revision 미고정)을 전부
막았습니다. 그러자 **gpt-oss-20b 에서 168축이 검사된 적이 없었다**는 것이 드러났습니다 --
`(T+1)+n_sink`, `w_local+n_sink` 가 평가 불가였는데, `n_sink` 가 "차원이 아니다"라고 표시돼
심볼 표에서 빠지면서 정작 라벨에는 쓰이고 있었습니다. namespace 를 고쳐 이제 평가됩니다.

그 상태로 네 모델 재검증: **축 865,820개, 미검증 0, 어긋난 라벨 0, 모두 PASS**
(Llama-4 76,730 / gpt-oss-20b 47,906 / 120b 71,426 / V4-Pro 669,758).

다만 이것은 **라벨이 배치에 대해 일관된가**를 볼 뿐이고, 말씀하신 대로 의미가 맞다는
증명은 아닙니다. 그래서 소스 대조를 부탁드립니다.

## 이미 모른다고 표시한 것

모델마다 `UNKNOWNS.md` 가 함께 나갑니다. 등급은 넷입니다.

* `open_tie` — 후보 둘이 **같은 값**이라 못 갈랐습니다. 구체 크기·FLOPs·바이트는 맞고
  **이름만** 미정입니다.
* `scope_inferred` — scope 정규식만이 갈랐고 아무도 검증하지 않았습니다.
* `heuristic` — **산술로 지어낸 이름.** 값은 맞지만 이름이 틀릴 수 있습니다.
* `unresolved` — 근거가 없어 정수로 뒀습니다.

여기에 더해 **"알고 받아들인 한계"** 절에 표가 안 보여주는 계산을 적었습니다(gpt-oss 의
GLU clamp, V4-Pro 의 mHC Sinkhorn·압축 가중합·Indexer head 가중합·hash/동적 routing·
inverse RoPE, Llama-4 의 chunked attention 이 마스크에만 있는 것). 표의 행 수로 연산량을
세면 과소평가된다고 명시했습니다.

**이 목록을 다시 지적하실 필요는 없습니다.** 다만 그중 소스로 바로 갈리는 것이 있으면
말씀해 주십시오 -- 지난번 `d_model`/`d_moe` 판정처럼 그대로 반영합니다.

## 물어보고 싶은 것

**Q1. 표의 op 구성이 그 모델의 forward 와 맞습니까.** 빠진 op / 없는 op / `block_type`
분할(어느 레이어 집합이 한 템플릿인지) / 모델 고유 기제가 표에 보이는지.
특히 이번에 늘어난 `add_` 행들이 제자리에 있는지 봐 주십시오.

**Q2. 축 라벨이 그 축이 실제로 세는 것과 맞습니까.** 폭인가 개수인가, 접힌 축
(`B*T`·`B*n_h`·`B*k*T`·`B*E*T`)이 정말 그 접힘인가, decode 의 크기-1 축과 캐시 길이,
가중치 축에 배치·시퀀스 이름이 붙은 자리.

**Q3. 위 "우리가 찾아 고친 것" 넷이 제대로 고쳐졌습니까.** 고친 방향이 소스와 맞는지,
과하거나 모자란 데가 없는지.

**Q4. 우리가 모른다고도 표시하지 못한 오류가 있습니까.** 이게 가장 값집니다.

## 지적하실 때

모델 / phase / `op_id`(또는 `module_path` + `op_type`) / 지금 → 맞는 것 / **파일:줄 근거**.
설치된 transformers 5.14.1 기준이 가장 좋고, 없으면 공식 리포지토리 커밋·URL 로 주십시오.
근거 없는 판정은 반영할 수 없습니다 -- 판정은 인용과 함께 `rules/label_overrides.yaml` 에
들어가고, 아무 축에도 안 맞는 항목은 게이트가 잡습니다.

자리 단위 원장이 `prefill.axis_resolution.jsonl` / `decode.axis_resolution.jsonl` 에
`(op_id, field, shape_index, axis)` 키로 있습니다.
