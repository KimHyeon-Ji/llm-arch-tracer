# Codex 검토 요청 — 14개 모델 결과물, 외부 소스만으로 독립 검증

## 반드시 지켜줄 것 — 이 요청의 핵심 제약

**이 저장소의 파이프라인/추출 코드는 전혀 보지 마세요.** `src/`, `rules/`, `mechanics.md`,
`develop/` 등 "어떻게 이 결과가 나왔는지" 설명하는 어떤 내부 코드나 문서도 참고하지 마세요.
(애초에 이 요청에는 그런 코드가 첨부돼 있지 않습니다 — 아래 첨부된 결과 파일들이 전부입니다.)

**대신 각 모델을 처음 보는 것처럼, 순수하게 외부 자료만으로 조사하세요**:
- 그 모델의 공식 논문/기술 리포트
- Hugging Face 모델 카드와 `config.json`
- 해당 모델의 공식 GitHub 구현체 (예: `transformers` 라이브러리의 modeling 코드, 또는 벤더가
  공개한 원본 레포)
- 벤더 공식 블로그/기술 문서

그 다음 아래 첨부된 **결과 파일**(`model_summary.md`, `structure.yaml` 등)에 적힌 주장 —
레이어 수, hidden size, attention head 수, head 폭, MoE 전문가 수, 파라미터 총량/활성량 등 —
이 그 외부 자료와 실제로 맞는지 하나씩 대조해주세요.

**이건 "이 저장소의 코드가 논리적으로 맞는가"를 묻는 게 아닙니다.** "이 결과물이 주장하는
숫자·이름이 그 모델의 진짜 아키텍처와 일치하는가"만 묻는 것입니다 — 저희 코드가 그 결론에
어떻게 도달했는지는 이 검토에서 완전히 무관합니다. 저희 파이프라인이 자체적으로 어떤 근거로
그렇게 판단했는지와 무관하게, **바깥에서 볼 때 이 숫자가 맞는지**를 독립적으로 재현해 판정해
주세요.

## 확인해줄 것 (모델마다)

1. **기본 스펙 일치**: 레이어 수, hidden size(d_model), attention head 수(n_h),
   head 폭(d_head), (MoE라면) 전문가 수·top-k·활성 파라미터 비율이 공식 소스와 일치하는가.
2. **아키텍처 계열이 맞게 식별됐는가**: 예를 들어 GQA인지 MHA인지, MoE인지 dense인지,
   RoPE인지 학습형 위치 임베딩인지 — `model_summary.md`의 서술이 실제 아키텍처와
   맞는가.
3. **의심스러운 숫자**: 값이 이상하게 크거나 작거나, 두 필드가 우연히 같은 값이라 서로
   바뀌었을 법한 자리가 있는가 (예: 두 서로 다른 개념의 폭이 같은 숫자로 나와서 이름이
   뒤바뀌었을 가능성).
