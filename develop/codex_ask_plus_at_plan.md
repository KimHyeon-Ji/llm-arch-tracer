## 2. 결정적 측정 하나 — 발행본에는 충돌 shape 이 없습니다

광역 selector 를 기각하게 만든 두 shape 이 **발행본 csv 에는 나타나지 않습니다.**

```
발행본 K3 csv 의 "맨 정수가 든 shape" 종류    prefill 37 종 / decode 36 종  (총 73)
그중 한 shape 에 맨 정수가 둘 이상인 것        0 종
[B, n_h_kda, 5, 5]                            발행본에 없음 (원시 원장에만 1,518 자리)
[B, n_h_kda, 5, d_chunk, 5]                   발행본에 없음 (원시 원장에만   828 자리)
```

즉 +@ 층이 **발행본만** 건드리면 그 충돌은 구조적으로 발생하지 않습니다. 이 사실 자체를
검사로 못 박았습니다(V3: 발행본에 맨 정수가 둘 이상인 shape 이 있으면 그 shape 을 자동
제외하고 사람에게 올린다).

## 3. 계획의 뼈대

### 산출물 구조 -- 원본을 덮지 않습니다

```
models/<model>/
  prefill.csv  decode.csv  prefill.jsonl  decode.jsonl     트레이서 원본 (불변)
  plus_at/
    prefill.csv  decode.csv  prefill.jsonl  decode.jsonl    +@ 적용본 (사용자가 쓰는 파일)
    substitutions.yaml   판정 = 항목 하나. 근거·반증조건·검토이력
    expressions.yaml     바꾸지 않았지만 식이 있는 축(실행 상태 축)
    symbols.yaml         심볼 범례. kind 로 아키텍처 / trace_control 구분
    DIFF.md              원본 대비 바뀐 셀 전수 목록
    REVIEW.md            다른 LLM 에게 그대로 주는 검토 요청서
```

### 기록 형식 -- 규칙 넷

```
1. match 는 shape 문자열 **전체 일치** + 축 위치
2. cells 는 **선언값**. 적용 결과가 다르면 스크립트가 멈춘다(조용한 과잉 적용 차단)
3. evidence 는 파일:줄 + 주장. 줄 번호 없으면 적용하지 않는다
4. falsifies 는 "틀렸다면 무엇이 달라야 하는가". 검토자가 이걸로 공격한다
```

### 검증 V1~V7 (하나라도 실패하면 **아무 파일도 쓰지 않는다**)

```
V1 격리       선언한 (shape, axis) 외의 모든 셀이 원본과 바이트 동일
V2 수량       항목별 바뀐 셀 수 == 선언한 cells. 총합도 일치
V3 충돌 부재  발행본에 "한 shape 에 같은 맨정수가 둘 이상" 인 경우 0
V4 형태 보존  행·열·열이름·op_id 순서 동일, shape 의 축 개수 동일
V5 csv==jsonl 같은 op_id 의 같은 자리가 두 파일에서 같은 문자열
V6 대입 검사  심볼에 symbols.yaml 값을 대입하면 원본의 구체값이 복원된다
              (n_chunk=5 -> 5,  N_route/C_trace = 15360/4 -> 3840)
V7 잔여 보고  바꾸지 않고 남긴 맨정수를 전수 목록화해 DIFF.md 에 싣는다
```

메타모픽 검사 M1(`T=384, d_chunk=64` 에서 청크 축 6 / prefix 5 유지)은 새 트레이스가
필요하므로 **미검증으로 표시**하고 절차만 적어 둡니다.

### 검토를 세 라운드로

```
R1 근거 검토    evidence 만 준다. **결론은 가린다.** "이 인용이 이 주장을 지지하는가"
R2 반증 검토    falsifies + risk 를 준다. "이 판정을 어떻게 깨뜨리겠는가"
R3 산출물 검토  plus_at/ csv 표본 + DIFF.md + 검증 결과. "표가 자기모순인가, 대입하면 복원되는가"
```

각 라운드를 **다른 세션**에 보내고, 답을 `substitutions.yaml` 의 `review:` 에 누적합니다.
판정이 바뀌면 항목을 지우지 않고 `superseded_by` 로 잇습니다.

## 4. 확인받고 싶은 것

### Q1. 이 층을 두는 것 자체가 정당합니까

트레이서 산출물을 후처리로 편집하는 것은 "게이트를 우회한다" 는 뜻입니다. 제 방어는
V1~V7 과 원본 보존뿐입니다.

**받아들일 만한 구조입니까?** 부족하다면 무엇을 더해야 합니까 --
(a) 원본과 적용본의 해시를 `substitutions.yaml` 에 박아 사후 변조를 막는다,
(b) 적용을 멱등으로 만들고 재적용 시 동일 해시를 요구한다,
(c) 게이트의 불변식 중 표만으로 검사 가능한 것(축 이름 중복, n_h/n_kv 배타, batch 축)을
    +@ 층에서도 다시 돈다,
(d) 그 밖?

### Q2. V6(대입 검사)이 충분한 방어입니까

제가 가장 믿는 검사입니다 -- "식에 값을 넣으면 트레이서가 실측한 구체값이 나와야 한다".
이게 통과하면 **적어도 이 트레이스에서는** 식이 맞습니다. 다만 스윕했을 때의 정확성은
보장하지 않습니다(그건 M1 의 몫이고 미검증으로 남습니다).

이 한계를 산출물에 어떻게 적어야 합니까? `verified_at_this_trace` / `unverified_under_sweep`
같은 필드를 항목마다 두는 것이 맞습니까?

### Q3. 계열 B 의 축 이름 (D1)

```
안 1   축을 `N_route/C_trace` 로 쓴다. 표가 자립하지만 trace_control 심볼이 표에 들어온다.
안 2   축은 리터럴 3840 으로 두고 사이드카에만 식을 적는다. 표는 순수하지만 스윕하려면
       사용자가 사이드카를 봐야 한다.
```

지난 판정에서 "roofline 에서는 전문가별 합성 분포보다 전문가 작업을 합쳐 `N_route` 로
계산하는 것이 낫다" 고 하셨습니다. 그렇다면 **표의 축을 아예 `N_route` 로 바꾸고 행을
합치는** 제3안도 가능해 보이는데, 그건 트레이서가 낸 행 구조를 바꾸는 것이라 망설입니다.
어느 쪽입니까?

### Q4. 계열 C 를 지금 손대야 합니까 (D2)

사용자 목적이 우선 **배치 크기 스윕**입니다. 고정 topology 에서 B 만 바꾸면 리터럴 유지가
맞다고 하셨습니다. 그러면 계열 C 는 `expressions.yaml` 기록만 하고 표는 그대로 두는 것이
맞습니까? 아니면 지금 indexed expression 으로 바꿔야 합니까?

`attn_res_block_size` 는 top-level config 에 없고 `text_config` 안에 있습니다 -- 확인해서
`floor(l/S)+2` 를 검증하겠습니다.

### Q5. 검토 라운드 설계가 독립성을 확보합니까

R1 에서 결론을 가리는 것으로 충분합니까? 저는 저자이면서 검증자이고, +@ 층은 게이트가
없어서 이전보다 더 취약합니다. 라운드를 더 쪼개야 합니까, 아니면 R1 의 가림 방식을
바꿔야 합니까(예: 후보 두 개를 주고 고르게 한다)?
